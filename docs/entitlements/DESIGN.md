# Customer Entitlements – design as implemented

Status: implemented, tested on in-memory replicas of the development data. **Not deployed anywhere. No migration has been run on any real database. Both rollout modes default to OFF.** Production needs separate approval for migrations and for every mode change.

## 1. What it does
A SuperAdmin decides, per customer company, which **modules → submodules → features** the customer can use. Core areas (Dashboard, Profile, Administration) are always on. Entitlements only **subtract** access: the existing RBAC (roles/permissions) is unchanged and still required.

Effective access of a node = `core OR (node active AND stored flag true for the node AND for all its ancestors)`.
- A missing row means disabled. New catalogue items therefore start disabled and show as **NEW** until the SuperAdmin decides.
- Flags are independent: switching a parent off/on never edits child rows, so re-enabling a parent restores the earlier child settings. Rows are never deleted.
- Existing customers are backfilled with everything enabled (Mobile App and HCF Portal included). New customers get core only; Mobile App and HCF Portal are off by default and changeable only by the SuperAdmin.

## 2. Data (master database; migrations 001–004, one transaction)
`application_modules`, `application_submodules`, `application_features` (catalogue: 11 modules, 63 submodules, 267 features), `endpoint_feature_map` (345 endpoints: 171 derived, 139 explicit, 35 exempt), `company_entitlements`, `company_entitlement_audit` (customer, user, time, old/new value, reason, batch), `entitlement_settings` (`mode`, `tenant_mode`), `entitlement_shadow_log`, `entitlement_coverage_daily`. Timestamps are `TIMESTAMPTZ`. 59 new permission codes (`*_VIEW` style) are inserted and **assigned to no role**.
Transaction database: `005` (`BULK_DOWNLOADS.company_id`, nullable) and `006` (`compliance_register.company_id`, nullable + partial index). Both additive, idempotent, run with `scripts/entitlements/run-transaction-migration.js --migration 005|006 --confirm <db> [--dry-run]`, which fingerprints every existing row and rolls back on any difference. **Run 005/006 before deploying the backend that maps the columns.**
Catalogue, endpoint map and the frontend route map are generated from one source (`scripts/entitlements/catalogue.js` + `build-seed.js`); a Jest spec fails if they drift.

## 3. Enforcement (global interceptor, after the existing guards)
Rollout modes, per switch: **OFF** (nothing), **SHADOW** (log what would be blocked, block nothing), **ENFORCE** (403). `mode` = licensing, `tenant_mode` = customer data isolation.
- **Licensing:** the endpoint's feature (any-of) must be effective for the caller's company (taken from the JWT). Unmapped endpoints fail closed in ENFORCE.
- **Platform admin** (SuperAdmin identity, `*` permission or superadmin role – the same definition as `PermissionsGuard`) is exempt from licensing and tenant rules. **Managing entitlements is restricted to the designated SuperAdmin identity only** (`EntitlementAdminGuard`); a `*` permission or a role name is not enough.
- **Channels:** the login channel is a **signed JWT claim** (`channel`: `DESKTOP` | `MOBILE` | `HCF_PORTAL`). Mobile logins send `channel: "mobile"` (`/auth/login`, `/auth/verify-otp`); HCF logins (both HCF token paths) set `HCF_PORTAL`. A session whose channel is not entitled is refused on **every** authenticated endpoint except reading its own entitlement state/permissions/branding and signing out. HCF accounts are also recognised by the account itself (`hcfs.hcf_id`), so tokens issued before this release are covered. The response is `403 FEATURE_NOT_LICENSED` with `feature` and a readable message ("The HCF Portal is not enabled for your organisation…"). **At login:** the auth use cases ask `CHANNEL_LOGIN_POLICY` (implemented by `EntitlementService.assertChannelAllowed`, provided by the global `EntitlementModule`, so the auth module needs no import of it) before any OTP or token exists. A customer user logging in with `channel: "mobile"` while the Mobile App is disabled, and an HCF logging in through `/auth/login` or `/hcf-auth/login` while the HCF Portal is disabled, get `403 FEATURE_NOT_LICENSED` with a clear message (ENFORCE), or a shadow-log entry (SHADOW), or nothing (OFF). The check runs only after the credentials are valid, so a wrong password is still `401` and the licence state is not revealed. SuperAdmin and wildcard-permission accounts are never refused; the second step of an OTP login (`/auth/verify-otp`) re-checks. The HCF login endpoint stays public (no `Authorization` header is needed) and behaves exactly as before for entitled customers. The API-level channel check above remains as a second line of defence for tokens issued before a channel was disabled.
- **Tenant isolation** (rules per endpoint in the map): DIRECT/VIA ownership lookups, body/query `companyId` checks, company-list filtering, customers cannot create companies, plus
  - `DIRECT_STRICT` – `compliance_register` (by `company_id`; rows without an owner are visible to platform admins only);
  - `VIA_FLEET` – `vehicle_waste_collections` owned through `vehicle_id → fleets.company_id` for list, create, update, submit, verify and delete; a vehicle without a company counts as nobody's;
  - `IN_CODE` – `GET /users/username/:userName` is scoped inside the controller: customer users are limited to their own company, platform admins may pass `?companyId=`. This one is always on, independent of the modes (it fixes an existing cross-customer lookup).
- **Company creation:** `COMPANY_CREATE` (RBAC) is still required. In tenant ENFORCE a non-platform user is additionally refused (a company created by a customer user would be a separate tenant it cannot see). Dev: no role other than `*` holds `COMPANY_CREATE`.
- **Bulk ZIP links (`/download/bulk/:token`, `/invoice-downloads/:token`):** the link is an emailed bearer link without a login, so ownership and entitlement are decided **at download time, on every use**. Owner = the recorded `company_id`, or, for legacy rows without one, the single company that all invoices listed in the ZIP's `manifest.json` belong to (read straight from the file without extracting it; nothing is written back). If the owner cannot be established safely (no readable manifest, a listed invoice no longer exists, invoices of several companies, unreadable/corrupt file) the link is refused with `403 DOWNLOAD_OWNER_UNVERIFIED` and a clear message, in every rollout mode. A platform administrator may still identify themselves with a normal `Authorization: Bearer` header. When the owner is known, its `FINANCE.INVOICE_MGMT.BULK_ZIP` entitlement is checked (mode dependent, like all licensing). Records and files are never changed or deleted. The download **history** lists tokens, so it is **always** limited to the caller's company, independent of the rollout modes (`EntitlementService.customerScope`): customers never see another customer's links, and legacy rows without an owner are hidden from customers (nothing is deleted; platform administrators still see everything; a customer account without a company gets 403). A link is an unguessable UUID valid 24 h.

## 4. Frontend
`EntitlementsProvider` loads `/entitlements/me`, refreshes on focus, every 60 s and after a `FEATURE_NOT_LICENSED` response, and fails open until loaded or when the mode is not ENFORCE. `canAccessDesktopModule`, hub-card filters, `ReportPage`, and `ProtectedRoute` (route gate → "Feature not available") use it; `AppLayout` and the hubs subscribe so sidebars and cards update without navigation. SuperAdmin screen `/admin/customer-entitlements` (customer selector, tree, Enable/Disable all, NEW/Active/Inactive/core indicators, confirmation with diff and reason, audit history, rollout panel with shadow report). The mobile web app signs in with `channel: "mobile"`.

## 5. Cache and cross-process invalidation (implemented)
Each Node process caches company flags (10 s), rollout modes (10 s), catalogue and endpoint map (5 min). A Save (`applyChanges`) and a rollout-mode change execute `pg_notify('entitlement_changed', <companyId> | '*')` **inside the same transaction/statement as the write**, so the notification is delivered only if the change commits. Every process keeps one dedicated `pg` connection that `LISTEN`s on that channel (`EntitlementChangeListener`, no external dependency) and drops the affected cache entries at once. Tested with two independent service instances over one database: the other instance sees a change within a few milliseconds (limit 1 s) although its TTL is 10 minutes.
- **Disconnect/reconnect:** a lost connection is retried with exponential backoff (0.5 s → 30 s). After every (re)connect all flag and mode caches are dropped, because notifications sent while disconnected were missed. While the listener is down the **10-second TTL is the safety net**. Failures (including a failing connection factory) never reach the application.
- **Requirement: a direct PostgreSQL connection.** `LISTEN` needs a session that stays open, so the listener's `host`/`port` (the master database settings, `MASTER_DB_HOST`/`MASTER_DB_PORT`) must reach PostgreSQL itself or a pooler in *session* mode. It does not work through a transaction-pooling proxy (PgBouncer `pool_mode=transaction`, RDS Proxy and similar). Not verifiable from this repository; see `PRODUCTION_READONLY_CHECKS.md` section 4.
- **Fallback configuration:** the 10-second cache TTL always applies (flags 10 s, modes 10 s). Without a working listener a change reaches other processes within at most 10 s, nothing else degrades; the listener keeps retrying with backoff (0.5 s to 30 s) and resyncs when it connects. `ENTITLEMENT_LISTEN=false` disables the listener entirely (no retries, TTL only). There is no other setting to change.
- `ENTITLEMENT_LISTEN=false` disables the listener (TTL only). The listener session shows as `application_name = entitlement-listener` in `pg_stat_activity`. It needs one extra database connection per process and a direct connection to PostgreSQL (a transaction-pooling PgBouncer in front of it would not deliver `LISTEN`; point the listener at a direct/session connection if one is used).

## 6. Rollout and the 14-day shadow plan
1. Run 001–004 (master) and 005, 006 (transaction) with `--dry-run`, then for real, after approval. 2. Deploy with both modes OFF. 3. Run `backfill-compliance-company.js` in report mode and review. 4. Set `mode` and `tenant_mode` to SHADOW for 14 days; review the shadow report daily (would-be blocks per route/customer, coverage counters, unmapped endpoints). 5. Fix mappings, then ask for approval before ENFORCE, tenant isolation first. Nothing in this branch changes a mode.

## 7. Compliance register back-fill (not run)
**No assumption is made about production:** the report below states, per row, whether it is attributable and why not otherwise.
`entitlements_006` adds the column only. `scripts/entitlements/backfill-compliance-company.js` (report-first) associates a row with a company **only** through `created_by → users.company_id`. Rows with empty/unknown `created_by` stay NULL. Previous code versions did not record `created_by`, so some or all rows may have an empty creator; that is for the report to show. `backfill-compliance-company.js` (read-only by default, also before migration 006; `--csv <file>` writes one line per row: id, proposed company, ATTRIBUTABLE/UNATTRIBUTABLE, reason) shows exactly which rows can be attributed; `--assign-unattributed-to <company>` is available for single-customer installations. Dev has 0 rows. **The production row count has not been checked (no production access); run the report there.**

## 8. Known limitations and outstanding risks
- Mobile channel binds to the login the client declares: a customer without Mobile App can still use the desktop login and the desktop-licensed features. The claim protects the mobile app, not the data behind shared APIs (those stay protected by feature entitlements).
- A session issued while a channel was enabled is refused at its next API call once the channel is disabled (login-time refusal only affects new logins).
- Tokens issued before this release carry no channel claim (HCF covered by account lookup). The JWT lifetime is `JWT_EXPIRES_IN` (default **24 h**; the production value must be read from the production environment). There is no refresh-token mechanism and the token is kept in `localStorage` (`mw-auth-user`) by both the desktop and the mobile app, so old sessions end by themselves within one lifetime. Until then a claim-less token counts as a desktop session (a mobile session of a customer whose Mobile App is later disabled is only caught after its next login). A one-time forced re-login for mobile is proposed but not implemented (needs approval).
- Cross-process invalidation depends on the listener connection (tested with two service instances against a real PostgreSQL server, including killed connections; the production connection path has not been checked); without it (or while reconnecting) a change can take up to 10 s to reach another process. Legacy download links whose owner cannot be derived from the ZIP manifest are refused (SuperAdmin with a Bearer token excepted); legacy rows are hidden from customers' download history; both disappear within 24 h as the links expire. Button-level hiding in the UI is a later phase.
- Jest cannot import TypeORM here (uuid ESM): integration/migration tests are Node harnesses in `test/entitlements/` over PGlite (not a project dependency).
- Deploy order matters: 005/006 before the backend; if the entity maps a column that does not exist, TypeORM queries on that table fail.

## 9. Mobile sessions issued before this release (proposal, not implemented)
- **Configuration:** token lifetime = `JWT_EXPIRES_IN`, default `24h` (`app.config.ts`, `.env.example`). The production value must be read from the deployed environment; without server access it can be read from any real production token: in the browser console `(p=>[new Date(p.iat*1000),new Date(p.exp*1000)])(JSON.parse(atob(JSON.parse(localStorage['mw-auth-user']).token.split('.')[1])))`. There is no refresh token; the token lives in `localStorage['mw-auth-user']`, one key for desktop and mobile alike.
- **Today:** a token without a `channel` claim is treated as a desktop session. It is never refused by the Mobile App check, so enabling/disabling Mobile App cannot wrongly log anybody out. No session is invalidated and the expiry is unchanged.
- **Natural migration (recommended):** deploy the backend and the frontend together. Every login (including every mobile login) after that carries the claim. After one token lifetime (24 h by default) every claim-less token has expired by itself; nothing else is needed.
- **If Mobile App must be enforceable sooner (needs approval):** (1) mobile only: when a `/mobile/*` page loads and the stored token has no `channel === "MOBILE"` claim (payload decoded locally, signature not checked, display purpose only), show "Please sign in again" and go to `/mobile/login`; (2) never touch `/` desktop routes; (3) because both apps share one `localStorage` key, signing out on a device also ends a desktop session in the same browser, so this prompt should be limited to mobile user agents or paired with a separate storage key per channel; (4) schedule it outside working hours and announce it. Nothing is invalidated server-side.
